# Jalan source contract

## Scope and request policy

Jalan is the only integrated hotel-discovery platform. Supported inputs are native landmark-directory URLs and six-digit property IDs. Other directory/property templates can return unknown; nationwide completeness is not claimed. Tourism-association and local official source directories belong in city-guide references, outside this discovery adapter. Property official sites can help verify material details.

Read-only public HTTPS GETs only. Ordinary search makes one request. Native radius search uses two reads for page 1 (landmark identity/point, then map candidates), or three for an explicitly requested later page (one additional XML read). A caller-supplied center still requires landmark identity validation. If the required native zoom is unsupported, a bounded directory/region-coordinate fallback uses at most four reads. Detail makes one, or two with `--rooms`. Each invocation has a hard four-attempt ceiling for radius search or two for other commands, serial request starts at least 1.5 seconds apart, a 15-second socket timeout and 4 MiB response cap. No retries, redirects, cookie jar, login, persistent cache, images or JavaScript execution. A socket timeout is not an overall command deadline. Do not retry a denied/throttled response with another client. Keep manual follow-up queries bounded.

Only `www.jalan.net` and the validated paths/parameters are accepted. Input directories have no query or fragment; filters/page are explicit CLI options. The tool generates `dateUndecided=1`, optionally `careBath=1` and `careStation5=1`. Caller-supplied arbitrary query fields, reservation engines and external hosts are rejected before network access. Radius mode additionally allows the matching `/kankou/spt_guideID/` landmark page and fixed `uww1701.do` map / `uww1702.do` paging routes. Native viewport requests allow only the generated center, zoom 11–20, hotel-only genre, re-search flag, undated/filter context and optional page 2–10 with its validated count. Landmark canonical ID, native name and publisher prefecture metadata must match the input. The fallback obtains region codes from the validated directory form and permits only paging index 30. The parser checks the main form's native spot/prefecture IDs, exact native heading, reflected filter checkboxes, page number and main-card counts. Unsupported or changed templates return unknown, not no hotels.

Jalan HTML is decoded as Windows-31J/CP932. Public readability is not a contracted API or permission to redistribute source data. Preserve attribution and links, follow Jalan's applicable site terms, and do not distribute captures/photos. The code's MIT license does not cover third-party content.

## Search output

Without a radius, main records come only from `a.jlnpc-yadoCassette__link` with native six-digit hotel IDs and `h2` names. Other hotel recommendations and room-plan cards are excluded. Introductions and access are read from dedicated main-card fields. Prices and availability are omitted, including undated starting rates.

`search --expect` is the exact native landmark name before the directory-heading suffix `周辺のホテル・旅館・宿泊施設`, not an arbitrary heading prefix. Preserve operator/name qualifiers; do not append `周辺`. Radius mode compares the same name against the landmark's native map name. Mismatches still fail rather than selecting a substitute.

`landmark_ja`, `directory_url`, `source_total`, `page`, `source_cards_on_page`, `returned_count`, `output_truncated` and `has_next_page` describe source and output coverage. Native filters are validated at page level; they are not independent verification of every hotel. No automatic relaxation, sorting or multi-page collection occurs. An explicit validated zero total on the first page is distinct from missing cards or a failed page. A missing/unsupported zero-results template can return unknown conservatively.

`walking_review.claims` retains minute claims and their native clauses. It does not assert a particular station, route, accessibility, luggage suitability or current construction status. `distance_claims` contains only explicitly walking-labelled metric distances in source access text, with the original clause. Generic distances and walking times are not converted into walking distances. `potential_conflict` is a conservative flag requiring inspection, not a definitive rejection. A selected station5 filter can conflict with the access text or concern another station. Preserve discrepancies instead of confirming the requested walking limit.

`operating_status` detects explicit full dates immediately followed by 開業/オープン/OPEN, optionally 新規. Future relative to retrieval JST becomes `planned_opening`. Otherwise status stays `unknown`; it does not infer “open” from the absence of a date. Trip suitability needs comparing the native notice with the travel dates.

## Straight-line radius filtering

`search --radius-m METRES` accepts 1–20000 metres. The CLI validates the matching landmark page's canonical ID, native name and publisher prefecture before querying candidates. Its default center is the `detailMap-canvas` WGS84 point, not a specific station exit. Optional `--center-lat`, `--center-lon` and `--center-name` must be supplied together with a radius. These caller-supplied decimal-degree coordinates must lie in the supported Japan bounds (20–46 N, 122–154 E); they retain `kind=user_supplied_coordinates` and no verified source. The landmark is still checked; the custom point is not geocoded or verified as an entrance.

Native radius queries use an initial radius of **`r + min(0.5*r, 1000 m)`**, then round the map zoom outward. `radius_filter.prefilter` records this candidate-sizing policy separately from the original radius. The zoom policy uses conservative angular half-spans of 0.0135 latitude degrees and 0.027 longitude degrees at zoom 14, doubling each at every lower zoom; longitude sizing accounts for latitude and the buffered spherical circle. These are client sizing bounds, not official server bounds or a guarantee of complete geographic coverage. Do not equate the page's visible map dimensions with a contracted search envelope. A hotel absent from a native result is never classified as outside the radius.

Supported native zooms are 11–20. When a larger radius needs a wider unsupported zoom, the CLI uses the directory/region-coordinate fallback instead of sending an unsupported query and accepting an empty result. `prefilter.mode=regional_coordinate_lookup` identifies that fallback. The combined margin remains in metadata as the requested policy, not a claim that the fallback applied it.

For `candidate_source=jalan_native_viewport`, hotel candidates come directly from the requested map page, not an intersection with a directory page. HTML main-card IDs/names must agree with the associated marker IDs/names/coordinates and counts. Initial candidates are native `div.pack#listresult-N` cards; later pages use the UTF-8 XML's associated property and marker records. Native center/zoom and reflected filters must agree with the request; mixed attraction/event results and unrequested facility filters are rejected. Scripts are parsed as data, never executed. No Google Maps runtime, image, key or third-party endpoint is fetched. This is the public website path, not the separate key-authenticated Jalan Web Services API.

Map candidates provide `introduction_ja`; they do not provide the directory's dedicated access field. `access_ja` is null and `walking_review` is empty. Walking claims in an introduction remain in that native text; read a shortlisted property's profile for its access section. Do not manufacture access claims from map distance or reinterpret introductions as a dedicated access field.

`source_total_scope=buffered_map_viewport` means `source_total`, `page`, `has_next_page` and `source_cards_on_page` describe the unfiltered native viewport, never all hotels in the original circle. Exactly one requested candidate page (up to 30 records) is evaluated per invocation; there is no automatic crawl. `--page 2` means native map page 2 in this mode. It requires reading the initial map context before the XML, but returns only page 2. Changed totals/zoom or inconsistent property/marker records fail with unknown state. Other source pages outside the returned page produce `partial`, even when every returned hotel's coordinates are known. An invalid or missing response is not an empty area.

For `candidate_source=jalan_landmark_directory`, ordinary directory pagination applies. In the radius fallback, its source total remains unfiltered and `source_total_scope=landmark_directory`. The coordinate lookup uses the native directory's prefecture/large-area/small-area codes and filters. The map can have a different region/order from the directory: intersect map points with that directory page by exact hotel ID and normalized full native name; never add extra map properties. At most two coordinate-map pages (60 records) are read. Missing/unmatched coordinates remain unknown; a failed second read preserves valid initial points. Neither a source's viewport nor a region lookup proves exhaustive inventory in the requested radius.

`distance.metres` is the locally calculated Haversine distance using mean Earth radius 6,371,008.8 m. This is approximate straight-line map distance, not walking/driving distance, a property boundary measurement or an entrance route. Radius membership uses the unrounded distance, then display rounds to 0.1 m; decimal output does not imply that level of positional accuracy. Points within 50 m of the radius boundary have `near_boundary=true`. This fixed review aid is not a confidence interval, provider error estimate or relaxed cutoff.

Radius filtering evaluates all candidates on the requested source page before the output limit, retaining source ordering and `source_rank`. `radius_filter` records the exact center, coordinate sources, lookup coverage/errors and matched/outside/unknown counts for this page. `distance_unknown_hotels` is a separate list with its own output-truncation flag. Such hotels are not counted as outside the radius. Missing coordinates or coordinate-lookup errors in the fallback produce `partial`. A native map/identity/schema failure returns unknown state; no alternative client or speculative retry is used. Source totals, pagination and `source_cards_on_page` remain unfiltered within `source_total_scope`. A page with zero matches is not evidence that the entire radius has no matching property; there is no automatic crawl or nearest-hotel ranking.

Walking measurements remain separately attributed publisher claims. Only explicit walking-labelled metric distances are normalized from access text; unlabelled distances and walking minutes do not produce metre values. Native clauses retain approximation, route and station qualifications. The CLI neither computes pedestrian routes nor certifies source walking-distance accuracy.

## Profile and rooms output

Profiles validate hidden `yadNo` fields and the unique native `h1.jlnpc-yado__subTitle` with the complete hotel name and `の施設概要` suffix. Embedded news headings do not identify the property. Missing or duplicate native headings still fail. Supported table sections cover access/parking, rooms/facilities, baths, amenities/services and the amenity grid. Each section retains native label/value fields and table rows with header/cell kinds and spans. Nested table rows can repeat their parent text. `state=unknown` means the section is missing, not that the property lacks the feature. Source text is preserved; no blanket per-room amenity booleans are inferred.

The amenity grid must be inside `shisetsu-amenityspec_body_wrap`. The separate accessibility container `shisetsu-gnlspec_body_wrap` reuses the table class, so its rows are excluded from the amenity grid. Missing grid containers remain unknown; duplicate grid containers or tables still fail. This does not independently certify accessibility or add accessibility fields.

Room pages validate the same ID/name plus `の部屋`. Only the table headed 部屋タイプ / 室数 / 広さ / 通常料金（消費税込み） supplies associated room types, counts and areas. Prices are omitted. Unrecognized area units remain native text with null numeric area. Photo captions are not merged into these records. Missing supported tables yield unknown; contradictory/changed columns yield errors. Notes retain room-specific qualifications such as centrally managed air conditioning. Profile room totals/sizes and room-page records may disagree: retain both with separate sources rather than inventing a single truth.

Room-read failure gives top-level `partial` and preserves the successful profile. Fatal search/profile/identity failures give `error`, `state=unknown`, exit 2. Successful and partial output exit 0, so inspect status and nested room state. Every live response carries its own URL/retrieval time; publisher update time remains null. Measured usage counts HTTP attempts/body bytes/elapsed and pacing time, not tokens or money.
